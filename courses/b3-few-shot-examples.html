Part 1 · covers Vanna accuracy research

Why examples work: LLMs imitate patterns 8 min live

An LLM does not "know" that units sold means SUM(quantity) and not COUNT(*). But show it one correct quantity-sum query in the prompt and it will reproduce the pattern - that is in-context learning, and it is the cheapest accuracy lever in the whole field. Here is where the examples sit in the prompt.

LiveTwo silent failures this lever kills5 min▶

Both of tonight's targets run fine and return plausible numbers - the dangerous family from b1. Neither is a schema problem; the tables and columns are right. They are pattern problems:

  • Q5, the COUNT-vs-SUM trap. "Top 3 products by units sold." The model writes COUNT(*) - counting order LINES, so a 5-bag line counts as 1 unit. One correct quantity query in the prompt teaches SUM(quantity).
  • Q6, the group-then-average trap. "Average order value." The model averages line items directly, so a multi-item order gets split into pieces. An example showing sum-per-order-then-average - group first, aggregate second - fixes the shape.

Vanna's team measured this rung on their own workloads: schema-only prompting scored ~3%, adding static SQL examples reached 20-60% depending on the model. That is their reported band, not an independent benchmark - but the shape (examples help a lot, then stall) repeats everywhere in the research.

Real world

The analyst whose old queries became the product. A retail data team piloting text-to-SQL got their first real accuracy jump without writing a line of new code: they exported the 30 most-run queries from their BI tool's history, paired each with the plain-English request it had answered, and dropped the best ones into the prompt. The model stopped inventing aggregation patterns and started copying the house style - date filters, the standard revenue join, the naming conventions. Your BI backlog is a free training set; b3 is where you cash it in.

DaybreakGPT at rung 3 - schema (b2) + two example pairs, then the question You are a SQL expert. Write one SQLite query. Return only SQL. Schema (linked tables only): CREATE TABLE products (product_id INTEGER PRIMARY KEY, name TEXT, category TEXT, price REAL, roast TEXT); CREATE TABLE order_items (order_id INTEGER, product_id INTEGER, quantity INTEGER, unit_price REAL); Example 1 Q: How many units of Sunrise Blend have we sold? SQL: SELECT SUM(oi.quantity) FROM order_items oi JOIN products p ON p.product_id = oi.product_id WHERE p.name = 'Sunrise Blend'; Example 2 Q: What is the average revenue per order? SQL: SELECT AVG(t.total) FROM ( SELECT SUM(quantity * unit_price) AS total FROM order_items GROUP BY order_id) t; Question: Top 3 products by units sold
Self-studyWhere few-shot sits in the research taxonomy2 min read▶

The IEEE TKDE survey on next-generation database interfaces sorts in-context-learning methods for text-to-SQL into five buckets: vanilla prompting (zero or few-shot, tonight's lever), decomposition (break the question into sub-problems), prompt optimization (choose the best examples and wording - Part 2 tonight is the manual version), reasoning (chain-of-thought style thinking before SQL), and execution refinement (use the database's reaction to improve the answer). This track walks the whole taxonomy: tonight covers the first and third, b6 picks up execution refinement, and b7's multi-candidate trick borrows from decomposition and reasoning. Nothing you meet later is exotic - it is all context and feedback engineering around the same frozen model.

Part 2

Example quality beats example quantity 7 min live

The 20-60% band is wide for a reason: WHICH examples you include matters more than how many. The model imitates whatever you show it - including your mistakes. Three rules keep the lever pointed the right way.

LiveThe three rules of example selection4 min▶
RuleWhyAnti-pattern
1 · Match the question's SHAPEA top-N example teaches top-N; it does nothing for a share-of-total question. Shape = aggregation pattern + join path + filter style, not topic.Ten customer-count examples for a revenue-ranking question
2 · Only verified SQLA wrong example is worse than none: the model will faithfully reproduce the bug. Every pair should have run in production or been human-checked.Pasting a half-finished query from someone's scratch notebook
3 · Keep them freshStale examples referencing renamed columns or retired tables re-introduce the loud failures b2 just killed.Examples written before last quarter's schema migration

Where good pairs come from: the BI backlog (questions analysts already answered, SQL already trusted), analyst query history (your warehouse logs it), and the golden set itself - though never test questions verbatim, or you are just memorizing the exam.

Self-studyHow many is K? The token-budget tradeoff2 min read▶

Every example pair costs prompt tokens, and prompt space competes with schema (b2) and, from b4, retrieved docs. In practice teams run K between 3 and 10: below 3 the model has too few patterns to match against; beyond 10 the returns flatten while cost and latency climb, and irrelevant examples start to distract more than they teach. The real fix for "which K" is not a bigger K - it is choosing the RIGHT K for each question at query time. Hold that thought for exactly one section.

The ceiling: static examples cannot cover the space 5 min live

Here is the trap in tonight's lever: your examples are STATIC - the same K pairs go into every prompt, no matter what is asked. Users ask questions in dozens of shapes. Whichever shapes your K pairs happen to cover get fixed; everything else stays broken. That is the plateau inside the 20-60% band.

LiveReading the plateau honestly3 min▶

Tonight's scorecard will land at 42% - a real jump from 25%, and every point of it came from pattern coverage. But look at what still fails: Q7 needs to know "active" means cancel_date IS NULL (vocabulary, not pattern), Q8 needs the monthly-rollup convention, Q4 and Q11 need a metric DEFINITION of revenue. No quantity of static example pairs teaches meaning - and stuffing in pairs for every conceivable shape blows the token budget while burying the relevant pattern in noise. Vanna's research ladder points the way out: static examples 20-60%, contextually RETRIEVED examples ~80% (their reported numbers). Same lever, aimed per-question. That is next session.

Flip the pattern traps ★ 14 min · everyone builds

DaybreakGPT below has schema linking ON (b2's rung) and few-shot examples OFF. Three questions loaded: the two pattern traps and one preview of the ladder's habit of exposing the next failure.

Ask Q5 with examples off. It runs fine and ranks products by COUNT(*) - order lines, not units. A silent failure: read the Why note, then check the verdict against gold.

Ask Q6 with examples off. Average of line items, not orders - runs, looks plausible, wrong. Silent again.

Toggle Few-shot examples ON. Re-ask Q5 and Q6 - both flip to matching gold. The pattern in the prompt became the pattern in the SQL.

Now ask Q10 (revenue per customer) both ways. Examples off: a loud error - it assumes an order total column instead of the two-join path. Examples on: the join path is right, the query RUNS... and silently includes cancelled orders. The ladder just exposed the next missing lever - the revenue definition lives in b5's semantic layer.

Check it against real SQL Don't take the verdict's word for it. Here is the gold Q5 on the same live database - swap SUM(oi.quantity) for COUNT(*) and re-run to reproduce the trap by hand. Watch the rankings reshuffle. 
SELECT p.name, SUM(oi.quantity) AS units
FROM order_items oi
JOIN products p ON p.product_id = oi.product_id
GROUP BY p.name ORDER BY units DESC LIMIT 3;

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · Asked for "top products by units sold", a model with no examples wrote COUNT(*). Why is that wrong, and why did nothing warn anyone?

The query executes and returns a plausible ranking - the silent family from b1. Units sold needs SUM(quantity), and the model only learns that pattern from a worked example (or, later, a semantic definition).

2 · Which example set most improves a prompt for the question "average order value"?

Shape beats topic and quality beats quantity. Ten count-by-city pairs teach nothing about grouping-then-averaging; an unverified query teaches its bugs. One verified pattern of the right SHAPE is exactly what the model imitates.

3 · Why do static few-shot examples plateau instead of climbing to the top of the ladder?

Static means one-size-fits-all: coverage stops at whatever shapes you picked, extra pairs cost tokens on every question, and meaning ("active", "revenue") is not a pattern at all. Retrieving the right examples per question - b4 - is the way past it.
