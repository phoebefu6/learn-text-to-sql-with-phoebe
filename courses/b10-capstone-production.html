Part 0

Where the accuracy came from

Ten sessions, one honest lesson: every point of accuracy you gained came from context, not from a bigger model. The model in every playground on this track never changed. What changed was what reached it - the right tables, worked examples, retrieved metadata, business definitions, and a retry loop. That is the whole discipline, and it is why the job title is context engineer.

The semantic layer dominated because most of Daybreak's remaining failures were silent metric errors - revenue that quietly counted cancelled orders, "churn" that meant the wrong table. That matches the published evidence: a semantic layer was the strongest measured lever in the field, not a bigger model.

Real world

The order of operations is the lesson. A team that jumps straight to "let's fine-tune a SQL model" skips the four cheaper levers that did most of the work here. The professional sequence is boring and effective: get the schema context right, add examples, retrieve metadata, define your metrics, then add a retry loop. Reach for a custom model only when all five are exhausted - which, in practice, is rarely.

Part 2 · covers production failure taxonomies, Spider 2.0 leaderboard

What changes in production 8 min live

100% on 12 curated questions is not 100% in production - it is a starting line. Four things break the moment real users and a live warehouse show up. None of them is the model.

LiveThe agent frontier - where the field is in 20264 min▶

The same lesson plays out at the research frontier. On the enterprise-grade Spider 2.0 benchmark, bare models scored 10-17%. By mid-2026 the leaderboard is dominated by agents - the top Spider 2.0-Snow entry sits near 96.7 (a leaderboard figure, and the benchmark's own annotation quality is contested - see b8). Agents win by doing exactly what you built: retrieve context, execute, observe errors, retry.

  • Agents beat bare models because they add context and correction loops at runtime, not because they use smarter base models.
  • Interactive settings are still hard: on BIRD-Interact, GPT-5 was reported to complete only 29% of tasks in agentic mode (a benchmark figure). Multi-turn, ambiguous, real conversation remains unsolved.
  • Read every leaderboard number skeptically - b8 showed why (annotation error rates of 50%+ on major benchmarks). Your own golden set on your own data still beats any public score.
Self-studyGovernance recap - how the vendors handle it2 min read▶

The commercial tools solve governance by staying inside their platform: Cortex Analyst keeps data and row-level security inside Snowflake; Genie inherits Unity Catalog permissions; Vanna v2 added a user-aware identity flow with row-level security for self-hosted deployments. The anti-pattern is the CSV-export tool (Julius-style) that pulls data out to an ungoverned sandbox - convenient, and a shadow-IT audit failure. If you build your own agent, the query must execute under the asking user's permissions, never a service account with god-mode. The leader track's a5 covers this from the risk-officer angle.

The capstone run: measure every lever's worth ★ 12 min · everyone builds

Run the full stack, then take levers away one at a time and watch the number fall. That drop is each lever's marginal value on this data - the single most useful experiment you can run on any text-to-SQL system.

Run the scorecard with all levers on - 12/12, 100%. That is your ceiling on this golden set.

Turn OFF semantic layer only, re-run. Watch it fall to 58% - the biggest single drop, because Daybreak's hard questions are metric-definition questions.

Turn semantic back on, turn OFF schema linking, re-run. Different questions break - the loud hallucinations return.

Note which questions are fragile (break when almost any lever is missing) versus robust. Those fragile ones are where you would spend curation effort first in production.

Prove it against real SQL Any answer you doubt, check by hand - this editor runs the same database. Compare the gold delivered-only revenue with what a semantic-off run produced. 
SELECT ROUND(SUM(oi.quantity * oi.unit_price), 2) AS revenue
FROM order_items oi
JOIN orders o ON o.order_id = oi.order_id
WHERE o.status = 'delivered';

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · DaybreakGPT went from 8% to 100%. Where did the accuracy come from?

Every lever was a context-engineering move. The base model was constant throughout. That is the thesis of the whole track: the model is not the product, context is.

2 · What re-triggers a full evaluation run in production?

Schema evolution is the quiet killer: a renamed column or new table breaks retrieval and definitions without any error. Re-run the golden set on every change - that is why you versioned it.

3 · What is the right scope for a first production pilot?

Scope small or fail - it matches Genie's own guidance (5 or fewer tables) and keeps the golden set tractable. Boiling the warehouse is the top adoption anti-pattern; expand only on measured evidence.
