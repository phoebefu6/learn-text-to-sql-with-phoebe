RAG over metadata: the right context, per question

Static examples (b3) plateaued because the same K pairs went into every prompt. Tonight you fix the aim: store MANY pieces of context outside the prompt - DDL, documentation, verified question-SQL pairs - embed them, and retrieve only the slices relevant to each question. This is the Vanna pattern, the architecture behind Databricks Genie rooms, and the single biggest jump on the whole accuracy ladder. It is also plain RAG - just pointed at metadata instead of documents.

Part 1 · covers Vanna architecture

The Vanna pattern: train on three collections 8 min live

Vanna - the most-starred open-source text-to-SQL framework, whose full story (including its 2026 archiving) waits in b9 - made one architectural decision that the whole field then converged on. You "train" the system not by tuning the model but by loading three collections into a vector store. At question time, you retrieve the nearest slices of each and assemble the prompt fresh.

LiveWhy retrieval beats stuffing4 min▶

b3 left us with a dilemma: more static pairs means better coverage but a fatter, noisier prompt on EVERY question. Retrieval dissolves it:

  • The corpus can be huge, the prompt stays small. Store 500 verified pairs and every doc note you have; each question retrieves maybe 5 chunks. Token budget solved.
  • Coverage scales with the corpus, not the prompt. New question shape failing? Add one pair to the collection - no prompt surgery, no redeploy.
  • Relevance is automatic. "How many active subscriptions" retrieves the subscriptions DDL, the doc line defining active, and the nearest pair - not the top-3-products example that would just be noise.

Vanna's own research puts numbers on it: static examples landed at 20-60% depending on the model, RAG-retrieved contextual examples reached ~80% - their reported measurements on their own workloads, so keep b8's skept-o-meter on, but the direction matches everything else in the field.

The assembled prompt for Q7 - every block below was RETRIEVED, not hard-coded You are a SQL expert. Write one SQLite query. Return only SQL. [retrieved DDL - nearest table] CREATE TABLE subscriptions (sub_id INTEGER PRIMARY KEY, customer_id INTEGER, product_id INTEGER, start_date TEXT, cancel_date TEXT, monthly_qty INTEGER); [retrieved documentation - nearest doc chunks] - An ACTIVE subscription is one with cancel_date IS NULL. - Dates are stored as TEXT 'YYYY-MM-DD'; monthly rollups use strftime('%Y-%m', ...); date math uses date(x, '+30 days'). [retrieved example - nearest verified pair] Q: How many customers have never cancelled anything? SQL: SELECT COUNT(DISTINCT customer_id) FROM subscriptions WHERE cancel_date IS NULL; Question: How many active subscriptions do we have?
Part 2

What documentation buys you: the vocabulary bridge 7 min live

Of the three collections, documentation is the one nothing earlier on the ladder could substitute for. Business vocabulary - the words your users actually ask in - appears NOWHERE in the schema. No schema dump and no query pattern carries it. Somebody has to write it down once; retrieval delivers it forever.

Self-studyWhere doc chunks come from in a real team2 min read▶
  • Your data catalog - column descriptions in DataHub, OpenMetadata, or Unity Catalog are already doc chunks; RAG is finally the tool that makes filling them in pay off.
  • Onboarding docs and wiki pages - the "how we define things" page every team has, half-finished. Chunk it.
  • Slack archaeology - the thread where someone asked "wait, what counts as active?" and a senior analyst answered. That answer is a doc chunk.
  • Failure mining - every silent failure your golden set catches names a missing chunk. Write the sentence, add it to the collection, re-run. That loop is b8's whole workflow.
Part 3 · covers Genie room anatomy (light) + learn-rag cross-ref (light)

You have seen this RAG before - and you will see it in every vendor 5 min live

If you took the learn-rag course, tonight should feel familiar: embed a corpus, retrieve top-k by similarity, assemble a prompt. Identical mechanics - the only difference is the corpus. Document RAG retrieves passages to ANSWER from; metadata RAG retrieves schema, definitions, and examples to WRITE SQL from. One skill, two aims.

LiveSpot the pattern in the products3 min▶

Once you know the three-collection shape you cannot unsee it in the commercial field:

  • Databricks Genie rooms are the pattern productized: a curated space over Unity Catalog metadata (collection 1), plain-text curator instructions (collection 2), and example SQL queries (collection 3) - retrieved per question. Documented limits are telling: max 30 tables per space, recommendation 5 or fewer - curated small corpora beat everything-dumps, exactly the b3 lesson.
  • Snowflake Cortex Analyst leans harder on structured definitions - a YAML semantic model - which is really b5's rung; more on that next session.
Real world

The Genie room that went 8/15 → 15/15. Databricks' own published walkthrough of setting up a Genie space starts with a fresh room scoring 8 out of 15 on its benchmark questions. The fix was not a model upgrade: curators added instructions ("active means no cancel date" style sentences) and example queries, iterated against the benchmark, and reached 15/15. That is tonight's demo, run by a vendor, on their product: collections in, accuracy out. The curation loop took real human weeks - the "curation tax" the leader track (a4) prices out.

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · What are the three collections a Vanna-pattern system trains on?

Schema text (DDL), business-meaning sentences (documentation), and worked examples (question-SQL pairs) - all embedded in a vector store and retrieved per question. "Training" loads collections; the model's weights never change.

2 · Why does documentation fix "how many active subscriptions" when a perfect schema dump cannot?

The vocabulary gap: users ask in business words, the schema speaks in column names, and no amount of schema detail bridges them. One doc sentence does - and retrieval delivers it to exactly the questions that need it.

3 · Same example pairs, same model - why do RETRIEVED examples outperform the same examples pasted statically?

Static prompting pays for every pair on every question and covers only the shapes you picked. Retrieval stores hundreds of pairs and delivers the nearest few per question - Vanna's reported band moves from 20-60% to ~80% on exactly this change.
