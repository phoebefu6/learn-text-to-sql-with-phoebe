Part 1 · the failure family levers b2-b4 cannot touch

Business meaning is not in the schema 7 min live

Look at Daybreak's schema as hard as you like: nothing in it says what revenue is. orders.status exists; the rule "revenue counts delivered orders only" does not. That rule lives in your head, your finance team's head, maybe a wiki - everywhere except the one place the model reads. A semantic layer is that rule, written down as a machine-readable contract: metric definitions, mandatory filters, blessed join paths, vocabulary rulings.

LiveFour silent failures hiding in plain sight5 min▶

Every question DaybreakGPT still misses at 58% is a meaning problem, and every one executes cleanly:

QuestionWhat the model doesThe missing ruling
Q4 · total revenueSums every order line - cancelled and pending includedRevenue = delivered orders only
Q10 · revenue per customerCorrect joins, correct math - forgets the delivered filterSame metric rule, applied everywhere
Q9 · March churnCounts cancelled ORDERS in MarchChurn = cancelled SUBSCRIPTIONS, a different table
Q11 · best channelRanks channels by order count"Best" means most revenue, not most orders

Not one raises an error. Not one looks wrong in a result grid. Each would sail into a dashboard, a board slide, a decision. This is the failure family we named in b1 - silent - and levers b2-b4 cannot touch it, because tables, examples and docs about columns all answer "how do I query this?", never "what did the business mean by that word?".

Self-studyWhy RAG docs (b4) did not already fix this2 min read▶

b4's retrieved docs handled vocabulary about columns: "active means cancel_date IS NULL", "dates are TEXT, roll up with strftime". Those are facts about the data. Metric rules are different beasts - they are policy: cross-table, mandatory, owned by the business, and dangerous to leave to retrieval luck. A semantic layer promotes them from "notes the retriever might surface" to "contract the system always honors". Rough boundary that serves well in practice: if getting it wrong changes a number an executive sees, it belongs in the semantic layer; if it just helps the model write tidier SQL, docs are fine.

Part 2 · covers arXiv 2604.25149, dbt-labs/dbt-llm-sl-bench

The evidence: strongest in the field 8 min live

Plenty of text-to-SQL claims are vendor smoke. This rung is the exception: it has a published paired benchmark, an open-source vendor benchmark you can re-run yourself, and an independent ontology result - all pointing the same direction.

LiveReading the three results honestly5 min▶
  • The paired benchmark (published, arXiv 2604.25149). Three frontier models, same questions, with and without a 4KB semantic document. Every model jumped +17 to +23 percentage points (from 45-50% to 67-69%). One small file moved the needle more than a model-generation upgrade typically does.
  • dbt's benchmark (dbt-labs/dbt-llm-sl-bench - vendor-run, but open source and re-runnable). Raw text-to-SQL scored 84-90%; routing through the semantic layer scored 98-100%, and 100% on in-scope questions. Treat the exact numbers as dbt's claim on dbt's benchmark - but the repo is public, which is more than most vendors offer.
  • dbt's sharper point is about failure modes, not points. Raw text-to-SQL fails silently - a plausible wrong number. A semantic layer fails loudly - an out-of-scope question returns an error, not a guess. Loud is safer: an error costs you a retry; a silent wrong number costs you a decision.
Real world

The ontology stack, cranked to eleven. One reported enterprise experiment (a blog-published result - hold it loosely) put GPT-4 on a 199-table insurance schema: raw text-to-SQL managed 16.7%. Rebuilding the target as an OWL ontology - a formal semantic layer - lifted it to 54.2%, and adding ontology-based query checking pushed toward 72%. Same model throughout. The uglier the schema, the more the meaning layer pays.

Self-studyWhy loud-by-design is the safer architecture2 min read▶

A semantic layer narrows what the system will attempt: questions map to defined metrics and dimensions, or they fail with "I don't have a definition for that". That refusal feels like a limitation in a demo and is a gift in production - it converts the invisible failure family (silent wrong numbers) into the visible one (errors you can log, count, and fix by adding a definition). You are not making the system smarter; you are making its ignorance honest. Keep this trade in mind for b8, where you will measure refusal and wrong-answer rates separately.

Part 3 · covers WrenAI MDL, dbt SL, Cortex Analyst YAML, Genie instructions

What a semantic layer looks like in practice 6 min live

Every serious product in this market ships the same idea in a different file format. Recognize the shape once and you can read all of them:

ProductThe contract's shapeFlavor
WrenAIMDL - a JSON modeling definition language of business concepts, joins and metricsSemantic-layer-first open source
dbt Semantic LayerMetrics defined once in dbt, queried by name instead of re-derivedLives where your transforms live
Snowflake Cortex AnalystA YAML semantic model - practitioners' verdict: "the magic is in the YAML"Warehouse-native
Databricks GenieCurated rooms: plain-text curator instructions + example SQL + benchmarksCuration-as-product

Here is DaybreakGPT's whole semantic layer - the document that buys tonight's 34 points. Read every line; each one is a Q4/Q9/Q10/Q11 ruling you met in Part 1:

daybreak-semantics.yaml - the metric contract the model reads metrics: - name: revenue definition: SUM(order_items.quantity * order_items.unit_price) required_filter: orders.status = 'delivered' note: Cancelled and pending orders NEVER count as revenue. - name: churned_subscriptions definition: COUNT(subscriptions) with cancel_date in the period note: Churn is about SUBSCRIPTIONS. A cancelled order is not churn. rulings: - phrase: "best channel" / "top channel" means: rank channels by revenue (see metric above), not order count joins: - revenue questions join orders to order_items on order_id; there is no total or amount column on orders
Self-studyWriting your own: three rules of thumb2 min read▶
  • Start from arguments, not tables. Every metric two humans have ever disputed in a meeting ("is that gross or net?") goes in first. If nobody disputes it, it can wait.
  • One definition, one owner, one place. The moment revenue is defined in two files, you have rebuilt the problem you were solving.
  • Small is fine - small is the point. The paired benchmark's document was 4KB. Ours is under 30 lines. Coverage of the disputed core beats encyclopedic sprawl you cannot maintain.

The playground below starts at b4's configuration: schema linking, examples and RAG on, semantic layer off. The four questions loaded are exactly the silent-failure family. Before you touch the new lever, make your predictions - that is the skill this session is really teaching.

Predict first. For each of Q4, Q9, Q10, Q11, write down what wrong answer you expect with the semantic layer off - which filter is missing, which table is wrong, which metric got swapped. Part 1's table is your cheat sheet; no peeking until you have committed.

Ask all four with semantic off. Every one returns rows and a "plausible but WRONG" verdict - four silent failures in a row. Score your predictions.

Toggle Semantic layer on and re-ask all four. Watch each flip to "matches the gold answer". Same model, same schema, same docs - one small contract changed.

Toggle it back off for Q10 and diff the two SQLs: the only change is WHERE o.status = 'delivered'. Thirty-four points of accuracy hanging on one line nobody had written down.

Verify one by hand Never trust a verdict you have not reproduced. Run the gold churn query below, then change subscriptions/cancel_date to orders/order_date with status = 'cancelled' and re-run - you will manufacture Q9's silent failure yourself and see the two different numbers side by side. 
SELECT COUNT(*) AS churned FROM subscriptions
WHERE cancel_date >= '2026-03-01' AND cancel_date < '2026-04-01';

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · dbt argues a semantic layer is safer than raw text-to-SQL even before counting accuracy points. Why?

Raw text-to-SQL guesses when it should refuse - and its wrong guesses run fine. A semantic layer refuses what it has no definition for. Loud costs a retry; silent costs a decision.

2 · Which of these belongs in the semantic layer, rather than in RAG-retrieved docs (b4)?

A and B are facts about the data - docs and schema territory. C is a business policy that changes a number executives see: a metric definition with a mandatory filter. Policy goes in the contract, not in retrieval luck.

3 · What did the paired benchmark (arXiv 2604.25149) measure when a 4KB semantic document was added?

45-50% → 67-69% for every model in the pair - the consistency across models is the point. The knowledge was missing from the context, not from the models' IQ, which is this track's thesis in one result.
