Part 1 · covers survey arXiv 2408.05109 framing

What a text-to-SQL system actually is 7 min live

Strip away the vendor gloss and every text-to-SQL product - Databricks Genie, Snowflake Cortex Analyst, an open-source Vanna deployment, the agent you build here - is the same four-stage pipeline. The differences that matter all live in stage 2: what context reaches the model.

LiveThe promise - and the 86% → 10% cliff4 min▶

"Just ask your data a question" is the oldest promise in BI, and LLMs finally made the demo work. On the academic Spider benchmark, frontier models score in the high 80s - which is why every demo you have seen looks flawless. Then researchers built Spider 2.0 from real enterprise databases (1,000+ columns, 100+ line answers) and the same models scored ~10%. GPT-4o: 86.6% on Spider, 10.1% on Spider 2.0.

  • The cliff is not a model problem. The models are identical in both tests. What changed is the gap between question and context: real schemas are huge, cryptic, and full of business meaning no schema dump carries.
  • Agents close it with context, not IQ. By mid-2026 agentic systems top Spider 2.0-Snow near 97 - by retrieving metadata, checking errors, retrying. Every one of those moves is a session in this track.
  • Your job title in this field is context engineer. That is the honest name for the work.
Real world

Salesforce shipped it and told the truth. Their production text-to-SQL agent launched at roughly 50% efficacy. The fix that got them to ~80% was not a better model - it was generating 10 candidate queries per question and scoring them (that trick is session b7). Production text-to-SQL is engineering around the model, not worshipping it.

Self-studyWhy this course simulates the model2 min read▶

Three reasons. Zero setup: everything on these pages runs in your browser - real SQLite via WebAssembly, no API keys, no bills. Determinism: a real LLM gives a different wrong answer each run, which makes terrible teaching; the simulator always makes the canonical mistake, so the lesson lands. Honesty: each simulated failure is drawn from the documented failure taxonomies - hallucinated columns and wrong schema picks alone cause over 80% of real execution failures in published error analyses.

When you want the real thing: the same golden-set method works with any live model, and session b9 maps everything here onto Vanna, WrenAI, and the LangChain SQL agent - where the "model" is Claude, GPT, or a local Ollama.

The naive baseline: schema dump and pray 8 min live

The obvious first build - paste the CREATE TABLE statements into a prompt, append the question - is where everyone starts, including the vendors. Here is what that prompt actually looks like, and the two ways it fails.

The entire naive DaybreakGPT - one prompt You are a SQL expert. Given this schema, write one SQLite query that answers the user's question. Return only SQL. CREATE TABLE customers (customer_id INTEGER PRIMARY KEY, name TEXT, city TEXT, country TEXT, signup_date TEXT, plan TEXT); CREATE TABLE products (product_id INTEGER PRIMARY KEY, name TEXT, category TEXT, price REAL, roast TEXT); CREATE TABLE orders (order_id INTEGER PRIMARY KEY, customer_id INTEGER, order_date TEXT, status TEXT, channel TEXT); CREATE TABLE order_items (order_id INTEGER, product_id INTEGER, quantity INTEGER, unit_price REAL); CREATE TABLE subscriptions (sub_id INTEGER PRIMARY KEY, customer_id INTEGER, product_id INTEGER, start_date TEXT, cancel_date TEXT, monthly_qty INTEGER); CREATE TABLE events (event_id INTEGER PRIMARY KEY, customer_id INTEGER, event_date TEXT, event_type TEXT); Question: What is our total revenue?

Real world

The BI team that piloted a chat-with-data tool. Week one: the demo wowed the exec sponsor on five rehearsed questions. Week three: a regional manager asked "revenue last quarter" and got a number 30% high - the tool summed list prices instead of order line prices and nobody noticed for days. That is a silent failure in the wild. The fix was not a new tool; it was defining revenue in one place the model could read (b5) and a golden set that would have caught it in minutes (tonight + b8).

Part 3 · covers Spider/BIRD execution-accuracy metric

The golden set: how you measure any of this 5 min live

You cannot improve what you do not measure, and you cannot trust a demo. The professional move - same one Spider and BIRD use, same one Databricks tells Genie curators to set up - is a golden set: real questions your business asks, each paired with SQL a human verified. Run the system, execute its SQL, compare result sets to gold. The match rate is execution accuracy (EX) - the only number in this field worth repeating.

LiveDaybreakGPT's 12 golden questions3 min▶

Our golden set spans the difficulty that kills naive systems: simple counts (Q1), correct column names (Q2-Q3), multi-table revenue with a metric definition (Q4, Q10, Q11), quantity vs line-count traps (Q5-Q6), business-vocabulary words like "active" and "churn" that appear nowhere in the schema (Q7, Q9), date handling (Q8, Q12). Twelve questions is small - real teams run 50-200 - but the mechanics are identical, and you can read every one.

Compare-by-result matters: two different SQL strings that return the same rows both count as correct. That is why the field measures execution accuracy, not string match - and why a golden set needs a database to run against, not just a file of expected SQL.

Self-studyWhere golden sets come from in a real team2 min read▶
  • Mine the BI backlog: the last 50 ad-hoc questions analysts actually answered, with the SQL they wrote - already gold-labeled by production use.
  • Interview the stakeholders the tool is for; their first 10 questions are your first 10 rows.
  • Include traps on purpose: every ambiguous metric ("revenue" - gross? delivered-only?) and every vocabulary word ("active", "churned") your org uses. Those are where silent failures live.
  • Version it and re-run on every change - schema migration, prompt tweak, model upgrade. b8 builds this into a habit.

Break DaybreakGPT, question by question ★ 14 min · everyone builds

Below is DaybreakGPT at rung zero - no schema linking, no examples, no retrieval, no semantic layer, no self-correction. Ask it the golden questions and watch both failure families with your own eyes. The SQL it writes really executes against Daybreak in your browser.

Ask Q1 (how many customers). It gets this right - even naive systems handle trivial questions, which is exactly how demos mislead.

Ask Q2 (Pro-plan customers). Watch a loud failure: it invents a subscription_tier column and SQLite refuses. You know instantly.

Ask Q4 (total revenue). Watch the dangerous one: it sums every order line including cancelled orders. The number looks perfect. This is a silent failure - read the "Why" note under the result.

Ask Q11 (best channel). It answers "most orders" when you asked "most revenue" - metric ambiguity, the failure a semantic layer exists to kill (b5).

Check it against real SQL Don't take the verdict's word for it. Here is a live SQL editor on the same database - run the gold revenue query yourself and compare with what the naive model produced for Q4. 
SELECT ROUND(SUM(oi.quantity * oi.unit_price), 2) AS revenue
FROM order_items oi
JOIN orders o ON o.order_id = oi.order_id
WHERE o.status = 'delivered';

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · Frontier models score ~86% on Spider but ~10% on Spider 2.0. What changed?

Same models, real databases: 1,000+ columns, 100+ line answers, business meaning that lives outside the schema. The cliff is a context problem, which is why every fix in this track is a context lever.

2 · Which failure is more dangerous in production, and why?

A loud failure announces itself and can be caught and retried by an agent. A silent one ships a wrong number into a real decision. Q4's cancelled-orders revenue is exactly this shape.

3 · What is execution accuracy (EX)?

EX compares results, not strings - differently written SQL that returns the same rows is correct. Merely running without error is not enough: silent failures run fine and are still wrong.
