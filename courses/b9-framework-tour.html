Part 1 · covers the OSS framework field, repo-verified facts

The four architecture axes 8 min live

Strip the branding and every open-source text-to-SQL project bets on one primary answer to "where does accuracy come from?" - retrieval (fetch the right context per question), a semantic contract (write the business meaning down once), model weights (fine-tune SQL into the model itself), or an agent loop (execute, observe, retry). Four axes; you have built three of them.

LiveThe Vanna lesson: the most-starred project went commercial4 min▶

This one is verified, not vendor spin: on March 29, 2026, vanna-ai/vanna - the most-starred open-source text-to-SQL framework, 23.8k stars, MIT license - was archived and made read-only. Last release: v2.0.2 on February 2, 2026. The team pivoted to the commercial Vanna Cloud; community forks (DataChat among them) carry the OSS torch.

  • Popularity is not permanence. Star count measures past enthusiasm, not future maintenance. An archived dependency still runs - but CVEs, dialect changes, and LLM API churn arrive with nobody home.
  • The architecture outlives the repo. Vanna's train-on-DDL/docs/pairs pattern is b4 of this course; you can rebuild it in an afternoon or adopt a fork. Understanding beats depending.
  • Plan the exit before the entrance. When you adopt any OSS framework here, write down what you would do if it archived tomorrow. For one of them, that already happened.
Real world

Teams woke up on March 30 with an archived core dependency. Anyone who had wrapped Vanna as their production text-to-SQL layer got a choice: freeze on v2.0.2 forever, migrate to a community fork, pay for Vanna Cloud, or rebuild the pattern in-house. Teams that had treated Vanna as "the b4 pattern with a convenient API" - understanding the retrieval architecture underneath - migrated in days. Teams that had treated it as a magic box faced a re-evaluation project. That gap is exactly what this track's build-it-by-hand approach buys you.

Part 3 · covers build-vs-buy guidance, leader a3 bridge

Which tool, when 6 min live

The axes become a decision rule once you add the org. Four common shapes:

LiveThe four org shapes and their default answers4 min▶
  • Embedding chat-with-data into your product → a component library on the retrieval axis (the Vanna pattern - via a maintained fork, or rebuilt in-house per b4). You control the UX; the framework supplies context plumbing.
  • Business-user self-serve with governance requirements → a semantic-layer platform (WrenAI-style: MDL contract plus RBAC, RLS, column-level permissions). Governance lives in the contract, not in prompt hope.
  • Already on Databricks or Snowflake → the warehouse-native route first (Genie, Cortex Analyst - leader session a3 covers that landscape). Your data never leaves, permissions come free, and the curation tax is the same one you would pay anyway.
  • Learning, prototyping, or a weekend proof → a DIY agent, exactly like this course: LangChain's reference flow (discover → inspect → generate → validate → execute → retry) is tutorial-scale on purpose, and everything transfers.

The fine-tuning axis (SQLCoder) is the specialist answer: worth it when you have thousands of curated question-SQL pairs, hard latency or on-prem constraints, and evaluation discipline (b8) to prove it beats context levers on your data. Note its caveat honestly: SQLCoder's beat-GPT-4 claim held on Defog's own sql-eval, not on Spider or BIRD.

Demo 1 of 2

DaybreakGPT is Vanna - the mapping, live ★ 10 min · everyone follows

Vanna's whole API is three train() calls that fill three retrieval collections. You built all three, by hand, with a golden set attached. Walk the mapping:

Vanna's training API - annotated with the session where you built each collection # 1. DDL collection - the schema the retriever can pull per question vn.train(ddl="CREATE TABLE orders (order_id INTEGER PRIMARY KEY, ...)") # = b2 schema linking: right tables and columns into context # 2. Documentation collection - business meaning in plain text vn.train(documentation="Revenue counts delivered orders only. Active subscription = cancel_date IS NULL.") # = b4 retrieved docs + b5 semantic definitions # 3. Question-SQL pair collection - worked examples to retrieve vn.train(question="Top 3 products by units sold", sql="SELECT p.name, SUM(oi.quantity) AS units FROM ...") # = b3 few-shot examples, made retrievable per-question in b4

Read call 1: the DDL collection is your b2 lever - schema linking. Vanna retrieves the relevant CREATE TABLE statements per question instead of dumping all of them.

Read call 2: the documentation collection is b4's retrieved docs carrying b5's semantic definitions - "revenue = delivered only" is literally the sentence that fixed your Q4.

Read call 3: the question-SQL pairs are b3's few-shot examples, upgraded to per-question retrieval in b4. Example quality beats quantity - same lesson.

The realization: you already built Vanna's architecture by hand - plus the evaluation harness (b8) its README does not give you. Frameworks are congealed context engineering.

Free exploration + the design exercise ★ 12 min · you decide

All five levers, no guardrails. Toggle any combination, ask any golden question, and think in axes: schema + examples + RAG is the Vanna quadrant; semantic is the WrenAI quadrant; self-correction is the agent loop any quadrant can add.

The design exercise - argue it like a design review For each scenario below, pick a primary axis, name the framework style you would start from, and defend it in two sentences. There is a defensible default for each - and a best answer only your constraints can pick.

SaaS startup embedding chat-with-data into its product. Consider: component vs platform, who owns UX, what happens if the dependency archives (you know one that did).

Bank data team serving internal business users. Consider: RLS and column permissions, auditability, where the semantic contract lives, why "prompt hope" fails review.

Solo analyst automating their own weekly questions. Consider: setup cost, the DIY agent path, whether a golden set of 10 questions is enough (b8 says how to know).

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · What is the market lesson of Vanna's March 2026 archiving?

The architecture (train on DDL + docs + pairs, retrieve per question) remains sound - it is this course's b4. What changed is maintenance: archived, read-only, commercial pivot. Stars measure past enthusiasm, not future support; understanding the pattern is your insurance.

2 · A bank data team needs business-user self-serve with row-level security, column permissions, and auditable metric definitions. Which axis fits first?

Governance requirements live naturally in a semantic contract plus platform permissions - written down, reviewable, enforced. Fine-tuning bakes knowledge into weights nobody can audit, and a bare DIY agent leaves RLS as an exercise. Warehouse-native tools (a3) are the same answer bought instead of built.

3 · What is the honest caveat on SQLCoder's "beats GPT-4" claim?

The weights are open (7B-70B on HuggingFace, CC BY-SA), but the headline number comes from the vendor's own eval suite. After b8's benchmark-audit lesson, the reflex should be automatic: whose benchmark, whose gold labels, would it transfer to my warehouse?
